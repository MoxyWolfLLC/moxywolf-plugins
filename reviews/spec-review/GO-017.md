The advisor sent back a checklist, and I verified each item against the plan text. I found no contradictions and six ambiguities.

**Coverage candidate (run, not listed as a contradiction).** *Coverage is mandatory* lets an item with unchecked coverage pass only if the owner records an exception at that head, and the owner makes that merge. GO-017.6 routes the coordinator's merge through `goal_run.py may ... merge`, which needs coverage `checked`. The owner's merge is outside that path, and GO-017.6's wording ("existing gates", "Nothing here changes either") doesn't forbid it. The path can be satisfied, so it isn't a contradiction. The plan doesn't say how an owner-made merge fits the swarm:
- Does `merged` record it?
- Does it count as "the coordinator's last merge" for the merge-gate target check?
- Does a `refresh` void the owner's exception, which is tied to a head?

I've listed this as A4.

**Dropped:**
- GO-017.9 against *Transcript-derived data*: the plan doesn't say the pilot events come from session files.
- GO-017.3 against GO-017.5 ("eligible again", "across attempts", "never redispatched"): launch failures and review blocks are separate mechanisms, so they don't conflict.

- **A4.** *Coverage is mandatory*, GO-017.6 and GO-017.7 don't say how an owner-made merge for unchecked coverage interacts with merge-gate, `merged` and `refresh`.
