# Spec review: DESIGN.md CC-002

_2026-11-18T05:36:02+00:00 · claude-sonnet-5-5 with claude-fable-5-2 advisor (1 calls)_

The advisor's four candidate contradictions don't hold up against the plan text, so I've listed every item as an ambiguity.

**Candidates checked and not listed as contradictions:**
- **Criterion 5 against criterion 8, request order.** The ordering rule and the "delete-record before hash check" rule can both be satisfied. The real gap is what `apply` does with a later request for a case whose `add` it left pending. That is A5.
- **"Owner confirms" against `--by`.** The plan reads "owner" as the executing principal and says "staging stays owner-only, so no one else confirms". I found no conflict.
- **"Writer never sees the folder without its pending request" against quarantine.** Both requirements are satisfiable. The publisher writes the request first, and quarantine only moves a folder. The risk is Drive sync order, which the plan doesn't address. That is A6.
- **Criterion 7's two retention bullets.** The `retire` bullet is only stated for held-out cases and for the "retired" state. The plan never says whether retiring a proposal case is allowed. That is A1.

**Ambiguities (all at item scope):**
- **A1:** Does `retire` apply to proposal cases? If it does, the date retirement plus 12 months always falls after the manifest's stated expiry of publication plus 12 months.
- **A2:** `status` runs `verify` first, and `verify` fails store-wide on a conflict copy. Does that make every case ineligible, or make `status` refuse? What exit code does `status` return, given it is documented as 0 or 3 only?
- **A3:** The constraint calls the manifest "write-once", but it is rewritten at `confirm` and again when `publish` adds the publication time. When does it become write-once? Does the confirmed file list and the second gitleaks pass still match after `publish` edits it?
- **A4:** `excluded_projects` is filled "at `init`". How is a project added later kept out of the opt-in question and out of `publish`?
- **A5:** `apply` processes requests in time order but leaves an `add` pending when its hashes don't match. What happens to a later `exclude`, `retire` or `delete-record` for that same case id in the same `apply` run?
- **A6:** The guarantee in criterion 4 that "the writer never sees the folder without its pending request" depends on Drive sync order, which the plan doesn't control. Criterion 8 quarantines a folder with no ledger line and no pending `add`. How is an in-flight published case protected from quarantine if the folder syncs to the writer first?
- **A7:** The preamble says every command refuses with `vault not mounted` when there is no mount and no Drive API writer. The "single serialized writer" section says cloud sessions drop requests in `inbox/`. How can a cloud session without a mount do that? How can criteria 1 and 2 (rating, opt-in and local staging) work there?
- **A8:** The "Test the boundaries" constraint bars a new "measurement report or score" before the boundary tests have run. Is the `status` readiness count, with its ready and not-ready thresholds, or the `/council-stats` change, new metrics work?
- **A9:** `confirm --retention <class>` takes a class. Criterion 7 says the manifest states the retention rule, "not a role or a date", and the role is set at `apply`. Which values are valid classes, and must the class match the role that `apply` later assigns? The quarter rule can give a case a role different from the one the class implied when it was confirmed.
