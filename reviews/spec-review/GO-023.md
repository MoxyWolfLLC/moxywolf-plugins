# Spec review: DESIGN.md GO-023

_2026-11-20T17:13:11+00:00 · claude-sonnet-5-5 with claude-fable-5-2 advisor (1 calls)_

Review of GO-023 against the plan's constraints: one contradiction and five ambiguities.

**Contradiction (C1), GO-023.8.** Bullet 2 accepts a successor's legacy string `start_after` entries only when its whole `DEPS.json` matches its pre-GO-023 predecessor's byte for byte. Bullet 3 lets the successor differ from that file by the entries for items its revised PLAN.md adds or removes. It also forbids every other change. Suppose the revised PLAN.md adds or removes an item. The file is then no longer byte for byte, so bullet 2 refuses the legacy entries that remain. Adding `because` to those entries is "any other change", which bullet 3 refuses through `goal_successor.py`. The bullet 3 test ("adds an item's entry (accepted)") cannot pass for any successor of a legacy predecessor.

**Ambiguities**
- **A1, GO-023.3 and GO-023.4.** The 30-claim test expects claims "not yet launched" to return to pending after a refusal at the 15th launch. GO-023.4 says that when every claim of one message was sent, none is "not yet launched". The plan doesn't say whether the 30 claims go in one message or several. GO-023.4 also gives two formulas for the new limit: "launched workers plus launches sent and not yet acknowledged", and "the launches still in flight after the refused one". The second drops the launched workers, so the test's expected limit can't be decided.
- **A2, GO-023.5 and GO-023.2.** The retest ceiling is both "the smaller of twice the limit and the number of ready items" and the approved `retest ceiling <C>`. The plan doesn't say what happens when C is above twice the limit, or what ceiling `tick` uses when C is below it. The approval's ceiling is not tied to a rule for the run's own ceiling.
- **A3, GO-023.4 and GO-023.5.** GO-023.4 says "each refusal lowers the limit or holds it at 1". During a retest a refusal sets the limit to the smaller of the current limit and the number running, and that can leave it unchanged. The plan doesn't say whether the no-endless-repeat argument still holds in that case.
- **A4, GO-023.10 and GO-023.4.** Test-drafting agents "hold no worker slot" but share the dispatch budget and the same host. The plan doesn't say whether a host refusal caused by their load counts in "workers running when the refusal came". It also doesn't say whether such a refusal lowers the host limit.
- **A5, GO-023.5 and the *pre-merge gate is GitHub's* and *A goal delegates item selection* constraints.** `swarm.py` verifies Dorian's retest approval and is the only writer of the host limit. The constraints list the goal-enforcing scripts that are `CODEOWNERS` paths, and `swarm.py` is not among them. It would therefore merge on machine review alone. The plan doesn't say whether it is meant to be owned.
- **A6, GO-023.9.** The proof reads the host record once, immediately before it starts. A refusal in the ceiling-3 run would write a limit that only a criterion 5 retest can raise. The 30-worker run is explicitly "not a retest". The plan doesn't say whether a record written by the first run stops the second.
