---
description: Run an approved goal (GO-003) — the plan's items committed straight onto goal/<id> (XE-049.5), one whole-goal review and one pull request into main, stopping on a regression, HALT, a changed goal, spend at 80% or an exhausted plan
allowed-tools: Read, Grep, Glob, Bash, Edit, Write, Agent
argument-hint: <goal-id> --pr <number of the PR that added the goal> [--builder <family>/<model>]
---

A goal is a brief Dorian approved (`goals/<id>/`, GO-001). This command runs it. It delegates which item to build next; it never delegates authority: nothing reaches `main` except through the goal pull request and its gates. Items commit straight onto `goal/<id>` with no pull request and no review of their own (XE-049.5); each item's tests still run through the check ledger, and the goal tests run after each item. The whole-goal cross-vendor review on the goal pull request is the review.

`goal_run.py` holds the run's state. It reads `main`, CODEOWNERS and the goal folder from the checkout it lives in, so run the copy inside a checkout of the governed repository, from that checkout's root, never the installed plugin's: `python3 plugins/gstack-execution/scripts/agent_token.py exec --goal-run -- python3 plugins/gstack-execution/scripts/goal_run.py ...`. `--goal-run` mints a token with contents and pull_requests only, so nothing in the run can add or change a workflow; the item builds run under it too, with `GSTACK_GOAL_RUN_DIR` set to the vault's goal-runs folder. An installed copy refuses. Every exit but 0 means stop.

1. **Start.** `goal_run.py start <id> --pr <N> --builder <family>/<model>`. It verifies the approval, refuses a builder whose family drafted or read the goal tests, refuses a token that reaches secrets, refuses when a workflow or deployment environment would deploy on a goal push, pull request or merge (GO-005.5), opens the goal ledger (GO-005.4), and opens `goal/<id>` from `main`. A refusal ends the command: report it to Dorian as written.
2. **Loop.** `git fetch origin main`, then `goal_run.py next <id>`.
   - `{"step": "brief_check", "items": [...]}` (XE-049.16): before any builder launches, write each listed item's builder brief to a file (the item text, its criteria and every command, script and tool you'll tell the builder to use) and run `goal_run.py brief-check <id> --item <n> --brief <file>`. A fresh model reads it and lists what's ambiguous or which tool it can't use. Don't edit `goals/<id>/`.
   - `{"step": "settle", "entries": {...}}`: settle each entry yourself where `DESIGN.md`, the goal brief or the named tool's own text answers it: change the builder's brief and run `goal_run.py settle <id> --item <n> --entry B<k> --as settled --how "<the change you made>"`. An entry only Dorian can answer: `--as needs_dorian --how "<the question>"`. That builder doesn't launch, Dorian is told (GO-006), and `next` exits 3 with `waiting_on_brief` until you record his answer with `--as settled --how "Dorian: <his words>"`. Other items carry on.
   - A failure (XE-049.17): when an item's tests fail, its review runs out of rounds, the holdout fails or the whole-goal review blocks, ask the agent that made the change "why did you make that choice?", quoting the failure, against its own transcript (resume it, or replay its transcript to it). Record the answer with `goal_run.py why <id> --failure "<the failure>" --answer "<its words>" [--item <n>] --family <its model family>`. The answer stays in the run state: show it to Dorian in your proposal, but never commit it, never send it to another model family, and never paste it into a later builder's brief. The run record and a later attempt's brief (`whys` in `next`'s step) carry its path in the run state instead. Tell a later builder to open that path only when it is of the `readable_by_family` family and runs on this machine and account; any other builder gets the path and the failure, not the text.
   - `{"step": "build", "item": ...}`: export `GSTACK_GOAL_LEDGER` as the printed `ledger`, then build that item in a worktree of the printed `branch_from` (the goal branch's fetched head, so it carries every item built before it), against the item's criteria, with its tests run through `check_ledger.py run` until the ledger is clear. Commit it there and push straight onto the printed `commit_to` (`goal/<id>`) once `goal_run.py may <id> --action vcs.push --resource goal/<id>` allows it: no item pull request and no item review (XE-049.5). Then run `goal_run.py merged <id> --item <n> --head <goal/<id> head after the push> --unsure "<what you're least sure of in this item>"` and loop; it refuses a head that doesn't build on the last recorded one. When the item can't be built (its tests won't pass, or it needs a change outside the envelope), run `goal_run.py failed <id> --item <n> --reason "<why>"`: the run stops there, and `goal_run.py record <id>` gives the record to report.
   - `{"step": "swarm", "items": [...]}` (GO-017): the goal was approved with a `DEPS.json`, so independent items build in parallel and integrate in dependency order. You are the one coordinator; workers never merge, dispatch, write run state, deploy or see the holdout. Workers are build workers: never claim a review or security role as a swarm item (review stays `/gstack-peer-review`), until a refused protected launch is shown on a real host even when the model-router hook can't start. The `--budget` is a dispatch budget, not a spend cap: it limits what is dispatched, and a running worker isn't stopped by it. A worker's full reservation stays charged when it reports; a `--cost` (dollars) only adds to it. A goal that needs a hard dollar cap is refused at start and runs serially or waits for a separate hard-capped-worker goal. First time: `swarm.py init <swarm_run> --goal <goal_dir> --base <goal/<id> head> --budget <what the spend ledger has left>`. Then `swarm.py tick <swarm_run> --halt <path of goals/<id>/HALT in your main checkout>` and launch one Agent worker per approved claim, all in one message so they run together. For a width above three, resolve the pre-send check below before sending. Launch each with `isolation: "worktree"`, `model` from `route.py recommend --subagent-type <type>` (MR-004; never rely on a hook to set it), the claim's base, branch, writable paths and pinned contracts, and the claim's `return` list as its whole report. Record `swarm.py launched` for each call the host accepted and `swarm.py launch-failed --reason "<the host's words>"` for each it refused: a refused launch is never reported as running. When a worker returns a patch rather than a head, `swarm.py apply-patch <swarm_run> <id> --attempt <n> --repo <checkout> --patch <file>` commits it on the claim's branch at the pinned base and prints the head. When a worker returns, `swarm.py result ... --head <its head> --repo <checkout> --tests passed|failed --cost <reported>`: the coordinator diffs the head against the claim and rejects writes outside it or to a pinned contract. An accepted head needs no review of its own (XE-049.5): integrate it onto `goal/<id>` only when `swarm.py merge-gate <swarm_run> <item id> --repo <checkout> --target origin/goal/<id> --halt <path of goals/<id>/HALT in your main checkout, freshly fetched>` prints `[]` (always pass `--halt`: a HALT raised while workers run must stop the merge); if the target moved, refresh the head on the target (`swarm.py refresh`, its tests again) first. Then merge the head into `goal/<id>` locally and push it once `goal_run.py may <id> --action vcs.push --resource goal/<id>` allows it, run `swarm.py merged`, `goal_run.py merged <id> --item <n> ...` (which refuses an item whose integration prerequisites haven't merged, or a head that doesn't build on the last one), and tick again. `swarm.py blocked` an item that can't go on: its dependents stop with it, unrelated items keep going. At the same time run `goal_run.py blocked <id> --item <n> --reason "<why>"`, which tells Dorian at once (an exhausted review escalates as `review_cap`) and leaves the run going. Run `goal_run.py failed` only when nothing else can proceed: every unmerged item is blocked or waits on a blocked one. `swarm.py status` shows what is running, waiting and why. HALT, the spend stop, the review cap and every gate below apply unchanged; a goal without `DEPS.json` gets `{"step": "build"}` as before.

     A goal's swarm is as wide as the items that can start together under its `DEPS.json` (no `start_after`, no overlapping `writes`), at most 10, unless `DEPS.json` sets `max_workers`, which wins; a goal with a `## Hard cap` section stays at three (XE-049.10). For any width above three, run `swarm.py launch-sent <run> <id> --attempt <n> --halt <path>` immediately before each corresponding Agent call, passing `--spend-stop` when applicable. Send only calls that print `launch`; reconcile each from the host response using `launched` or `launch-failed`, adding `--host-refused` only for a real capacity refusal. A sent but unanswered call keeps its reservation through stops and restart. Do not resend an unresolved call. The shared host record can lower that run’s ceiling, never raise it; retest is not available.
   - `{"step": "finish"}`: every goal test passes. Finish:
     1. `goal_run.py finalize <id>` commits the run record, the approved holdout (read by code from `~/.goal-holdouts/<id>.py` and checked against `holdout.sha256`, GO-002.8) and, when the brief's `## Release companion` is `marketplace`, the marketplace's top-level version bumped above `main`'s, as one commit straight onto `goal/<id>` on the head where the goal tests passed. No pull request and no review: the whole-goal review is pinned to the tested head, so the holdout never enters a review surface (XE-049.5).
     2. `goal_run.py propose <id>` opens the goal pull request from `goal/<id>` into `main` and prints `review_lanes`, min(10, the files the goal changes, max(2, its worker width)). Put that number in the whole-goal review's packet as `review_lanes`, so the review runs in that many parallel lanes; `may` refuses a review whose packet carries another number (XE-049.13). An item has no review and no lanes.
     3. Run `/gstack-peer-review` on that pull request's whole diff (a fresh cross-vendor review, coverage `checked`), pinned to the head before the finalize commit (where the goal tests passed) so the holdout file never enters the review surface. When it has no blocking findings and `goal-envelope`, `goal-tests`, `goal-holdout` and `tests` are green at the pull request's head, merge it as the bot, pinned to that head, once `goal_run.py may <id> --action merge --resource main --head <its head> --review <the review id> --pr <n>` allows it (GO-011.2). `may` checks that the review's packet names every item and starts where `main` and the goal head meet, Dorian doesn't review the pull request. When the whole-goal review's lane is `closed` (the goal carries a migration or another closed path or effect), `may` also needs Dorian's merge-instruction on the pull request (`peer_review.py merge-instruction`, posted as the agent): this is where the closed lane holds, since the items' closed lanes were deferred to it (GA-011). Ask him once, for this pull request, with what closed it.
     If `main` moves while the goal pull request is open, bring `goal/<id>` up to date with `goal_run.py sync <id>`: it merges `main` into the finalized head, holds the marketplace's top-level line at `main`'s while the plugin entries merge and then bumps it again above `main`'s, refuses any other conflict, pushes the merge straight onto `goal/<id>` and rebinds the goal pull request through `resync` (GO-004.1 as amended by XE-049.5); the checks rerun on the new head. A sync changes what merges, so the earlier review no longer counts: review again, pinned to a local commit on the new head that only deletes `goal-runs/<id>/holdout.py` (`git rm`, never pushed), so the surface carries what the sync brought and still not the holdout. `may` refuses the merge into `main` until that review is clean.
     4. If `goal-holdout` fails, run `goal_run.py holdout-failed <id> --detail "<what goal-holdout reported>"`; the run ends. If the whole-goal review in step 3 ends with blocking findings, run `goal_run.py review-failed <id> --review <its id> --detail "<the blocking findings, one line each>"`; the run ends the same way, because a fix would move the head the goal tests and the holdout passed at. Either way, don't touch the holdout or the tests, don't ask Dorian to override, and don't merge by hand. Report to Dorian what failed, with a proposal for the next goal; it starts only when he approves it like any goal. Successor goals are retired (XE-049.6): `goal_new.py successor` refuses, `goal_successor.py` refuses a successor folder in `tests`, and `goal_run.py start` refuses a successor id.
   - Safety stops still reach Dorian (GO-011): spend at its stop, a change outside the envelope, a ledger refusal, and a judgment call the council splits on or that isn't in-envelope code. They're the only questions during a run. When one means the goal itself is wrong, say so and propose the next goal rather than asking him to override.
   - exit 3 with `escalations`: an escalation holds the run (GO-006.2). Tell Dorian what it says, then record his acknowledgement in his words: `goal_run.py ack <id> --escalation <n> --words "<what he said>"`, and loop.
   - exit 3: a judgment call waits for Dorian. Ask him the printed question with its options and the code's reasons for the type, then record his answer in his words: `goal_run.py answer <id> --call <n> --choice <option> --words "<what he said>"`, and loop.
   - exit 1: the run has ended, `stopped` or `exhausted`, with its reason. Stop and report it to Dorian.
3. **Judgment calls (GO-005).** When an item needs a choice the plan doesn't settle, record it before acting: `goal_run.py call <id> --question "..." --options '["a","b"]' --proposed-by <family/model> --framed-by <family/model> --head <the item branch head>`. Code types the change; the agent's own label doesn't count. A type of `in_envelope_code` goes to the council: ask two models from families other than the builder's and each other's, one told to argue against the leading option, and record both with `goal_run.py council <id> --call <n> --votes '[...]'`. Unanimous decides; split waits for Dorian. Every other type waits for Dorian.
4. **Before every action (GO-005.4, .5).** Before each push, pull request, merge, review dispatch or outside call in the run, ask the runner: `goal_run.py may <id> --action <class> --resource <r>`. The classes and resources: `vcs.push <branch>`, `pr.open <base><-<head>`, `merge <target> --head <sha> --review <review-id> --pr <n>` (into `main` only the goal pull request after `propose`, under GO-011.2 as in finish step 3; items no longer merge through pull requests, they push to `goal/<id>` under `vcs.push`, XE-049.5), `review.send_code <reviewer>`, `external.model_call <model>`, `net.connect <host>`. Exit 0 means go. Exit 2 is a malformed call (an unknown class, a resource in the wrong form, a merge without `--head` and `--pr`): it prints the form expected, writes nothing and escalates nothing, so fix the call and ask again (GO-013). Exit 1 means stop: either the ledger doesn't grant it, which makes it Dorian's call (ask him, as for exit 3), or what a push, pull request or merge would set off has changed since the start, which has stopped the run. A ledger refusal is also an escalation that holds the run: relay it, and record his acknowledgement with `ack` before anything else proceeds. `finalize` and `propose` ask on their own. An `in_envelope_code` call never grants an action the ledger doesn't; the ledger is the agent's own record, so GitHub's rulesets are what actually hold.
5. **Resuming after a restart (GO-003.12).** `goal_run.py resume <id> --repo <owner/name>` reads the run's persisted delivery record, re-observes GitHub (the pull requests and the check runs at each candidate head) and the review records, records a merge only from GitHub's own answer, and then carries out each allowed action in turn without asking: the merge through the same gate `may merge` uses (one request per change per process, persisted before it is sent, so a lost response is found by the next observation and never answered with a second request), the release record through `peer_review.py record-release` (an existing record of that merge is reused, never rewritten), and each required checkout through `goal_delivery.py sync-checkout`, which fast-forwards a clean checkout on its branch or reports `sync_pending` with the checkout and the reason and changes nothing. It prints `delivery_status` (`complete`, `in_progress`, `sync_pending` or `blocked`) with what it executed and what stopped it; when delivery is complete it ends the run complete with the goal merge recorded. Everything it reads is the shared durable record under `GSTACK_GOAL_RUN_DIR`, so a fresh session on any machine with that record picks the delivery up where it stopped. Nothing a model declared establishes a merge or an approval; an unreadable budget or authority record blocks the run, and a gate that holds stops it. A merge counts only when GitHub reports this change's own pull request, in its repository and into its target, merged at the candidate head; required checks count only with the binding to this pull request, target and current base; an ended or held run is read but advances nothing; a merge request an earlier process persisted is never sent again, only re-observed; and every completion decision re-reads each required checkout instead of trusting a saved `synced` record. The goal pull request's change (`"final": true` in the delivery record) is the one exception to the exact-head rule. It merges its finalized head, and that counts only when `goal_run.final_review_pinned` finds the whole-goal review pinned to the tested head without its holdout and the head is the one finalize recorded. `record-release` accepts that relationship the same way, reading the goal run's record. Every Git read behind an observation or a synchronization is checked for its exit code, so a failed read is `sync_pending` and never reads as clean. A required checkout is bound to its repository, by `repo` or its github.com remote, and must contain every verified merge of that repository into its branch. `sync-checkout --merge` takes them comma-separated, and `goal_delivery.py status` observes each checkout against them. `goal_run.py complete` records the goal merge and, while release records or synchronization are outstanding, leaves the run open for `resume` to finish.
6. **After the goal pull request merges into `main`:** `goal_run.py complete <id> --pr <its number> --merge <merge sha>`. It records `complete` only when GitHub shows that pull request from `goal/<id>` merged into `main` as that commit, at the head whose goal tests passed. Then `goal_run.py record <id>` for the run record. No release bump follows: finalize moved the top-level version on the goal branch (XE-049.5), and `goal-envelope` refuses a top-level version that isn't above `main`'s. Then `/gstack-usability <id>` (GO-011.4).

**Agent viewer (optional, Mac only).** `swarm.py viewer-start <swarm_run>` starts the agent-flow viewer pinned at agent-flow-app 0.9.6 and prints its address, `viewer: http://127.0.0.1:<port>`; `swarm.py viewer-stop <swarm_run>` ends it. It runs only on a Mac with `npx`, and listens only on 127.0.0.1. The first start of agent-flow-app adds its own hooks to your `~/.claude/settings.json` and sends session events to a relay on 127.0.0.1; `swarm.py` itself never opens that file. A missing viewer never stops the swarm: where it can't run, `viewer-start` says so on standard error and exits 0.

**Messages (GO-006).** Any command can also print `{"messages": [...]}`: digests (one per merged item and one at the end) and escalations. Send each to Dorian as it's printed, as written, with PushNotification when it's available and in the conversation either way. A digest asks nothing; don't wait on it. An escalation that holds the run comes back as exit 3 from `next`. The run record keeps every message, so one that doesn't reach him is still on file.

Never edit `goals/<id>/`, the state folder or the ledger by hand. A changed goal is a new goal, approved again.

## Any repository: local mode (GO-010)

In a repository that isn't set up for goal mode, `goal_run.py` can't run (it reads its gates from the repository's own `main`). Run the goal in local mode instead, with the same order and the same stops, and with no setup asked of Dorian:

1. **Branch.** Push `goal/<id>` from `origin/main` as the bot.
2. **Items, in `PLAN.md`'s order.** Build each through `/gstack-build` as a pull request into `goal/<id>`. Before merging it: a clean cross-vendor review at its head, the repository's own checks green there, and `goal_local.py check <target> <id> <item head>` from the moxywolf-plugins checkout with every invariant passing, no outcome test that passed at the last item now failing, and an empty envelope error list. Then merge it as the bot, pinned to the head. A failure on any of those stops the run; report what failed. Three blocking review rounds on one item escalate to Dorian (DR-113).
3. **Finish.** When every goal test passes at the goal branch's head, run `goal_local.py check <target> <id> <head> --holdout ~/.goal-holdouts/<id>.py`. The script reads the holdout and checks its hash; never open it yourself. It must pass. Then a fresh cross-vendor review of the whole `main...goal/<id>` diff, clean.
4. **Goal pull request.** Open `goal/<id>` into `main` with the goal tests, the holdout result and the review ID in the body, and say it ran in local mode. Merge it as the bot, pinned to the head step 3 checked (GO-011.2); a closed lane needs Dorian's merge-instruction first, as in finish step 3 (GA-011). Then `/gstack-usability <id>`.
5. **Record.** Write the run's summary to `GSTACK_GOAL_RUN_DIR/<id>/RESULT.md`: outcome, items, each `goal_local.py check` result, the reviews.

Stop conditions still hold: a HALT file on `main`, spend at 80 percent of the cap, a deploy to an environment the brief names as Dorian's call.
