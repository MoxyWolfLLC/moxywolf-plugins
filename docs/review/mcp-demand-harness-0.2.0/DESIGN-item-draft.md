## Fifteenth objective: the demand harness

Opened 2026-10-26. `plugins/mcp-demand-harness` turns what a product's customers will ask its MCP server and REST gateway into tests, and the deterministic half of those tests is the probe: a direct `tools/call` or REST request with a check on the reply. The 0.1.0 probe graded any non-empty reply as a pass. On 2026-10-25 a 36-case baseline against STIGViewer production scored 36/36 under 0.1.0 grading; a later run of the same case IDs under 0.2.0 grading, against the same server build, scored 30/36 (the original saved responses were not regraded, since 0.1.0 kept no bodies), and nine of the thirty-six (25%) turned out never to have tested what their question text says: three never reached their endpoint, four hit a slug that does not exist, two used the wrong search mode, one graded a correct refusal as content, and empty role searches passed as answers. The premise of this objective: **a green probe must mean its declared checks passed, and a failure the server reports inside a 2xx reply is a failure.** A liveness or negative-only check cannot establish that the server answered the question; only a structured or content check can, and every layer says which kind it carries.

**Settled decisions**

- **Deterministic probes are graded by code only.** No model reads a probe reply. The model-driven suites (MCPJam, mcp-eval) stay separate and are not covered by this item.
- **Structured contracts, not substrings, are the strong form.** A `json_any_of` contract is a list of alternative branches; a branch is a conjunction of JSON Pointer predicates (`path`, `type`, `nonempty`, `equals`). A substring check proves an envelope arrived; a contract proves the shape of the answer.
- **Only one failure is excusable, and only explicitly.** A 2xx reply carrying `ok:false` passes only as a `not_found` denial with HTTP status 404 whose body matches a branch that names `/absence/reason` and a nonempty `/absence/message`. Authentication, entitlement, rate-limit and server-error envelopes never pass, whatever the contract says.
- **`error` and `isError` are reserved keys** at the top of any payload. A product whose success payload needs a field by those names renames it or nests it; the grader does not relax for everyone.
- **Evidence is kept, bounded and redacted.** Each layer records a receipt: sha256 of the canonical original body, up to 16,384 characters of sanitized text, and explicit `truncated` and `redacted` flags. Redaction is best-effort and says so. A truncated or redacted receipt cannot support exact offline regrading, and the report does not pretend otherwise.
- **A run never overwrites a run.** Output paths are opened exclusively; an existing file refuses the run before any request is sent.
- **Staging by default; production needs a named approver** (unchanged from 0.1.0, `GOVERNANCE.md`).

### DH-001 — A green probe means its declared checks passed

**Status:** review. Built on `build/mcp-probe-evidence` (harness 0.2.0, frozen at `b55a9e0`, fixes through `85d5f4a`). Cross-vendor reviews `20261026-080924-da4beb3-htsmx86c` (codex, 2 rounds, F1–F3 fixed at `c32cd54`) and `20261026-082123-182cc9e-sas80u0x` (codex, 3 rounds, F1–F3 fixed at `613f858` and `85d5f4a`, final round zero findings, `rounds_exhausted` on execution evidence at the reviewed head). Not released. Coverage against this item not yet scored; the item did not exist when the reviews ran. Evidence at the time of drafting: 82 tests at `85d5f4a`, failure-ledger run `331c2d9bb407`, exit 0, receipt verified by the dispatcher at open of a later review is still pending.

**Links introduced:** a probe result layer now links to its response receipt (sha256 of the original body plus bounded sanitized text), to the plan item that produced it (plan sha256 and the plan's declared bank hash), and to the harness that graded it (source hashes of `probe.py`, `probe_checks.py`, `demandlib.py`), with the server's self-reported name and version beside them. The links are hashes over content in the run record; nothing links to a deployed commit, and the record says so.

1. A `tools/call` reply fails the `mcp_payload` layer when it carries a JSON-RPC `error`, an `id` that does not match the request, `isError: true`, or empty data. Empty is decided by the selected payload: `structuredContent.data` when `structuredContent` is present, otherwise the first JSON text block's `data`; accompanying prose never makes an explicitly empty payload non-empty, and prose alone counts only when no block is JSON. Tests: `test_tool_and_http_errors_fail_before_content`, `test_rpc_errors_malformed_and_wrong_id_cannot_be_results`, `test_empty_text_and_text_failure_envelopes_fail`, `test_f1_text_cannot_make_empty_structured_data_nonempty`, `test_r2_f1_prose_cannot_make_empty_json_text_data_nonempty`, and `test_error_results_cannot_pass_a_nonempty_check` through a real subprocess run against a local HTTP fixture.
2. Every JSON envelope in a reply is inspected for an application failure: `structuredContent` and each parseable text block. An envelope with `ok:false` fails unless it is a `not_found`/404 denial matched by an explicit typed-absence branch of the case's `json_any_of`; `rate_limited`, `unauthorized`, `forbidden`, `error` and any non-404 status cannot borrow a success branch or an absence branch. A reserved `error` or `isError` key in any envelope's payload fails. Tests: `test_error_denial_cannot_use_a_success_branch`, `test_application_exceptions_in_text_are_not_success`, `test_f2_failure_envelope_in_any_block_is_seen`, `test_r2_f3_reserved_error_keys_apply_to_every_envelope`.
3. A REST layer passes its transport check in exactly two cases, consistent with criterion 2: a successful 2xx response whose body is a non-empty JSON object or array without an application failure, or the narrowly permitted typed absence, a 2xx body with `ok:false` whose denial is `not_found` with status 404 and which matches an explicit typed-absence branch evaluated against the whole body (REST contracts are body-relative; nothing is unwrapped). Every other `ok:false` body, and any reserved `error` or `isError` key, fails. Tests: `test_rest_json_error_is_not_success`, `test_r2_f2_rest_body_accepts_only_an_explicit_typed_absence`, `test_r2_f2b_rest_absence_is_body_relative_even_with_a_data_field`.
4. A `json_any_of` contract is validated before any request is sent: a non-empty list of non-empty branches, each predicate a JSON Pointer `path` with at least one of `type` (`object`, `array`, `string`, `boolean`, `number`, `null`), `nonempty: true`, or `equals`; an invalid contract in the bank or the plan refuses the run with zero requests. Grading evaluates every predicate of a branch and passes when any branch holds; a missing path fails; `equals` keeps JSON types apart at every depth, so `true` is not `1` inside objects or arrays; a structural check is never excused by a substring appearing elsewhere in the reply. Tests: `test_bad_contract_is_refused`, `test_structured_success_or_explicit_absence`, `test_nested_payload_and_pointer_escaping`, `test_f3_equals_keeps_json_booleans_and_numbers_apart_recursively`, `test_invalid_contract_is_refused_before_traffic`, `test_payload_json_contract_is_validated_and_exportable`.
5. Each layer records `assertion_strength` as `structured` (a `json_any_of` contract), `content` (`must_contain`), `negative_only` (`must_not_match` only) or `liveness` (nothing but non-emptiness), and `results.py ingest` renders a coverage table by strength and marks reports written before the label existed as `unknown_legacy` rather than inferring strength from a green verdict. Tests: `test_probe_retains_assertion_strength_and_flags_legacy`, `test_receipts_and_structured_contract_survive_real_http_run`.
6. Each layer keeps a response receipt: sha256 of the canonical original, up to 16,384 characters of sanitized text, `truncated` and `redacted` flags, and the original byte count. Redaction covers the run's own credential, keys named like secrets, bearer tokens, GitHub tokens and JWT-shaped strings, inside JSON text blocks and SSE `data:` lines as well as top-level fields, and safe JSON reformatting is not reported as redaction. Tests: `test_receipt_redacts_then_bounds_and_records_original_hash`, `test_json_text_secrets_are_redacted`, `test_sse_secrets_are_redacted_without_flagging_safe_json`, and the subprocess run asserting the fixture token never appears in the report.
7. A run record carries the plan file's sha256, the profile file's sha256, the bank hash the plan declares (labelled as the plan's declaration, not an independent bank check), sha256 of the three harness source files, the local git revisions of the harness and the working repository, and the `serverInfo` name and version observed at `initialize`. The record states that a version or surface digest is not proof of a deployed commit. Test: `test_receipts_and_structured_contract_survive_real_http_run`.
8. Before any request: an output path that already exists, an `--only` selection that matches nothing or names only items with no executable call, or an invalid contract refuses the run with exit 3, and the existing output is left byte-identical. Production still requires `--approver "First Last"` and refuses draft questions. Tests: `test_existing_output_and_empty_selection_refuse_before_traffic`, `test_invalid_contract_is_refused_before_traffic`, `test_production_needs_named_person`.
9. `demandlib.validate_bank` validates `json_any_of` in both `payload` and `rest` sections through `probe_checks.validate_contract`. The import is deferred to the point of validation rather than taken at module scope: `demandlib` still depends on `probe_checks` whenever a bank carries a contract, but loading `demandlib` for export, seeding or reporting does not import the probe module. Test: `test_payload_json_contract_is_validated_and_exportable`.
